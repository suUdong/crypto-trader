### 2. Time-of-day filter 23:00-03:00 KST blackout
- **Audit claim**: ₩-117,938 cumulative loss in 23:00-02:00 KST entries.
- **Verification on current jsonl**:
  - 23:00-02:00 KST window: n=61, total ₩-17,273, avg ₩-283/trade, WR 39.3%
  - Outside this window: n=331, total ₩-131,099, avg ₩-396/trade, WR 28.4%
  - The "graveyard shift" is **better** than the rest of the day.
- **Real worst hours (current data)**: 08:00-12:00 KST (morning Asian
  session) ≈ ₩-100k cumulative across ~84 trades.
- **Decision**: SKIP. Audit's 23-02 finding does not reproduce on the
  current trade set. A blackout there would block one of the only
  windows performing above the cross-day average.
- **P1 validation steps before any time filter is added**:
  1. Bucket the next 100 closed trades by KST entry hour.
  2. Apply a Bonferroni-corrected one-sided expectancy test per hour
     bucket. Implement filter only if a contiguous 3-hour band shows
     significantly negative expectancy with n>=20 per bucket.
  3. Run the same analysis again 50 trades later; require persistence.

### 3. Increase `atr_stop_loss` multiplier by 15-20%

  broader re-enable.

### 4. Symbol-level circuit breaker (3 losses in 48h auto-disable)
- **Status**: NOT IMPLEMENTED.
- **Decision**: SKIP. This contradicts the project's standing rule
  against "system on top of system" (see CLAUDE.md project rules).
  Auto-disable layers add hidden state, increase reload churn, and
  obscure which signal is actually driving entries when the user
  inspects logs. The data signal is also achievable with manual
  weekly wallet rotation off `scripts/leaderboard.py`.
- **P1 validation steps if revisited**: design must include
  (a) explicit visibility in dashboard, (b) per-symbol cooldown reset
  on first profitable trade, (c) integration test covering manual
  override.

### 5. Holding-period rules (30-min no-exit) and confidence floor
- **Audit claim**: low-confidence trades are universally bad
  (avg ₩-1,913), and short holds (<1h) lost ₩-113,601 cumulative.
- **Verification on current jsonl**:
  - `min_entry_confidence = 0.30` is already enforced globally.
  - Only 5 trades exist with `entry_confidence < 0.10`, all losses
    totalling ₩-9,568 — these predate the floor enforcement.
  - No trades exist in the 0.1-0.2 or 0.2-0.3 bands.
  - Higher confidence bands are NOT discriminating:
    - 0.3-0.5 → ₩-466/trade (n=47)
    - 0.5-0.7 → ₩-336/trade (n=173)
    - 0.7+   → ₩-351/trade (n=167)
  - Per-trade expectancy is similar across these bands, so raising the
    floor would just shrink sample size without flipping the sign.
- **Decision**: SKIP raising the floor. The minimum holding period
  ("no-exit-in-first-30-mins") is also skipped — it would suppress
  hard stops in volatile entries and the audit doesn't quantify the
  expectancy of trades exited within the first 30 minutes.
- **P1 validation steps**:
  1. Compute expectancy over trades held <30m (entry-time → exit-time
     delta) vs >=30m, segmented by wallet and exit_reason.
  2. Only consider a holding-period rule if <30m trades show a
     persistently larger negative expectancy after excluding
     hard-stop exits.

### 6. Regime-adjusted sizing (smaller positions in late bull)
- **Status**: NOT TIGHTLY VERIFIED.
- **Decision**: SKIP for now. The macro adapter already applies regime
  multipliers (`_REGIME_MULTIPLIERS`), and the audit's bull-vs-sideways
  finding (avg ₩-2,551 in bull, ₩-361 in sideways) needs cross-checking

- **P1 validation steps**:
  1. Re-bucket trades by `entry_macro_regime` if that field is logged

  2. Confirm the bull underperformance is concentrated in a small

     fade-the-trend in bull) before applying a global regime cut.
  3. Tune `_REGIME_MULTIPLIERS["expansionary"]` only if the effect
     is wallet-class-wide, not symbol-specific.
